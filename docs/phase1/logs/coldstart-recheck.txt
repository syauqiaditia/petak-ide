=== Jalur boot yang dicek (kode) ===
- ui/main.ts: cuma pasang window error/console listener (murah), lalu `mount(App, ...)` — tidak ada
  kerja berat sebelum mount.
- ui/App.svelte onMount(): urutan (1) listen fs-changed (murah), (2) load recent folders + auto-open
  recent folder folder pertama — SUDAH di-defer pakai `setTimeout(..., 20)` (komentar eksplisit: "deferred
  so initial window/editor paint is instant" — ini sudah dioptimasi sebelumnya, bukan regresi baru),
  (3) registerKeymap (murah, cuma addEventListener), (4) cek testMode utk auto-test (P12/P14/P15) — no-op
  di build release biasa.
- Editor.svelte onMount(): createEditorState() langsung (vim+CM6 extensions, doc kosong/tab awal),
  `new EditorView(...)`, lalu `requestAnimationFrame x2` baru panggil onReady -> markReady (yang men-trigger
  PETAK_READY di backend Rust). Tidak ada font loading blocking (`index.html` load Google Fonts pakai
  `media="print" onload="this.media='all'"` — non-blocking async pattern, sudah benar dari fase 0).
- preloadAllLanguages() (tree-sitter WASM preload) HANYA dipanggil di dalam runBenchmark() (App.svelte:371),
  BUKAN di jalur boot normal — dicek `grep -n preloadAllLanguages ui/` cuma 1 pemanggilan, di dalam bench.
  Jadi tree-sitter TIDAK ikut di-load sebelum first paint pada boot normal (palette/xterm juga masih
  lazy-import via `import('./features/.../X.svelte')`, dicek grep `import(` di App.svelte: Palette,
  TerminalPanel keduanya dynamic import saat pertama dibuka, bukan eager).
- Bundle chunk utama (`dist/assets/index-*.js`) = 653.39 kB (gzip 197.17 kB). Tidak ada angka fase 0
  utk dibandingkan (`docs/phase0-report.md` tidak mencatat ukuran chunk js, cuma ukuran .app/.dmg total).
  Palette (11.61 kB) dan TerminalPanel (335.74 kB) sudah terpisah jadi chunk sendiri (lazy), tidak masuk
  index chunk utama.

KESIMPULAN: tidak ada kerja non-kritis baru yang keliatan berjalan SEBELUM first paint di kode fase 1 —
auto-open recent folder sudah di-defer, tree-sitter/palette/terminal sudah lazy. Selisih ke budbudget
(690-692ms vs 686ms) kemungkinan besar dari overhead WKWebView + Tauri runtime start yang sama seperti
fase 0 (Mac fase 0 juga pernah dapat 739ms/752ms di kondisi lain), ditambah kondisi mesin tidak steril
(Chrome+Brave jalan, swap terpakai 2.4GB). Tidak ada fix "murah" yang jelas untuk dipangkas lagi tanpa
masuk optimasi besar (out of scope task ini) — perlu keputusan UQi apakah FAIL ini diterima/di-waive
atau perlu investigasi startup Tauri/WebView lebih dalam (di luar scope P1.10).
