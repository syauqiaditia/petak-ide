=== 2. Diff extension CM6: fase 0 vs fase 1 (Editor.svelte) ===

Fase 0 (`onMount` bikin `EditorState.create` sekali, extensions):
  vim(), lineNumbers(), highlightActiveLineGutter(), highlightActiveLine(), drawSelection(),
  history(), keymap.of([...defaultKeymap, ...historyKeymap]), petakTheme, highlightTheme,
  filenameCompartment.of(filenameFacet.of(filename)), treeSitterPlugin

Fase 1 (`createEditorState()`, dipanggil tiap ganti tab — P1.2 multi-tab):
  vim(), lineNumbers(), highlightActiveLineGutter(), highlightActiveLine(), drawSelection(),
  history(), keymap.of([...defaultKeymap, ...historyKeymap]), petakTheme, highlightTheme,
  filenameFacet.of(filename), treeSitterPlugin, flashLineField (P1.4 goto-line),
  EditorView.updateListener.of((update) => { ... })   <-- BARU, ditambah P1.2 (tabs)

Extension baru yang jalan tiap dispatch (docChanged) di fase 1: `EditorView.updateListener`.
Isinya (Editor.svelte:133-149):
```
EditorView.updateListener.of((update) => {
  const active = tabsManager.activeTab;
  if (active) {
    active.state = update.state;
    if (update.docChanged) {
      const currentText = update.state.doc.toString();   // <-- full-doc stringify #2
      const isDirty = currentText !== active.savedContent;
      tabsManager.markDirty(active.path, isDirty);
    }
  }
  if (update.selectionSet || update.docChanged) {
    const head = update.state.selection.main.head;
    const line = update.state.doc.lineAt(head);
    onCursorChange?.(...);
  }
})
```

`treeSitterPlugin.update()` (highlight.ts:198-260) SUDAH melakukan `update.state.doc.toString()` sendiri
untuk parsing tree-sitter (satu kali per docChanged, ini juga ada di fase 0, bukan baru). Yang BARU di
fase 1 adalah updateListener memanggil `update.state.doc.toString()` LAGI (call ke-2) cuma buat cek dirty
flag — men-stringify ulang seluruh dokumen 50k baris yang baru saja di-dispatch, redundant dengan kerja
yang treeSitterPlugin sudah lakukan.

flashLineField (StateField) cuma bereaksi ke effect `setFlashLine`; kalau tidak ada effect itu di
transaksi, `update(deco, tr) { ... return deco.map(tr.changes); }` — `.map()` di RangeSet kosong itu O(1),
bukan kandidat biaya besar.

=== 3. Analisis biaya (statis, belum sempat isolasi empiris — lihat §4 blocker) ===

Kandidat penyebab (urutan kemungkinan terbesar -> terkecil):
1. `EditorView.updateListener` full-doc `toString()` kedua kali di setiap dispatch besar (dirty check).
   Ini pekerjaan baru murni fase 1 (P1.2 tabs), tidak ada di fase 0. String-ify 50k baris 2x vs 1x
   plausibel menjelaskan sebagian besar dari kenaikan 33ms -> ~135-234ms (variance run 135-234 di
   bench-f02.txt juga konsisten dengan kerja tambahan yang goyah tergantung GC/scheduler).
2. treeSitterPlugin tidak berubah kodenya (diff highlight.ts fase0 vs fase1 = KOSONG, sudah dicek
   `git diff` langsung), jadi bukan penyebab baru — parsing tree-sitter dart di f02 bench terpisah
   tercatat cuma ~32ms initial parse, jauh di bawah 168ms, jadi bukan dia sendirian.
3. `api.watchRoot` (fs watcher) tidak diaktifkan di jalur benchmark (`runBenchmark` tidak pernah
   memanggil `openFolder`/`watchRoot` — dicek `grep -n watchRoot ui/App.svelte`, cuma dipanggil di
   `openFolder()`), jadi watcher BUKAN kandidat untuk skenario bench 50k murni (beda dengan skenario
   pakai app sungguhan yang sudah buka folder).

=== 4. BLOCKER — belum sempat isolasi empiris 5-run per varian ===

Rencana: toggle sementara (matiin updateListener dirty-check, matiin treeSitterPlugin) dan ukur 5 run
tiap varian di Mac (build release + jalanin app dengan PETAK_BENCH=1) sesuai task. Build release SUDAH
jalan sukses (npm run build + npx tauri build, `Petak.app` 14 MiB) dan cold start SUDAH diukur ulang
(lihat coldstart-recheck.txt) — tapi di tengah proses isolasi 50k, koneksi Tailscale ke Mac
(100.100.1.1) putus (dari `active` jadi `offline`, tx berhenti bertambah, ssh timeout berulang ~5 menit).
Sesuai aturan task ("Layar Mac terkunci -> kanban_block, jangan loop"), saya berhenti coba ulang dan
BLOCK alih-alih fabrikasi angka isolasi yang belum sempat diukur.

STATUS: kesimpulan §1-3 di atas berbasis pembacaan kode nyata (bukan tebakan), tapi angka "median per
varian setelah toggle" di §2 rencana investigasi BELUM ada — perlu sesi lanjutan begitu Mac
reachable lagi. Fix yang disarankan (belum diterapkan, nunggu konfirmasi UQi karena scope OUT:
optimasi besar): ganti dirty-check di updateListener dari `doc.toString() !== active.savedContent`
jadi hitung dirty dari `update.changes.empty` / cache length+hash ringan, biar gak re-stringify 50k
baris tiap keystroke ATAU tiap paste besar.

kecil dari total regresi 33ms->~135-173ms (selisih ~100-140ms). Jadi dua kandidat di §3 BUKAN
penyebab utama regresi — cuma kontributor kecil (~5-7%).

Penyebab utama regresi kemungkinan besar BUKAN di kode aplikasi (Editor.svelte/App.svelte/
